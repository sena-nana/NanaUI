# Component Content Layout and Migration Audit

A component retains semantics, interaction and chrome. Ordinary box arrangement belongs to Layout Foundation; `ComponentGeometry` is the draw projection of published parts. This page records the #205 migration boundary; an unmigrated row cannot be claimed as accepted on the strength of this document.

## Current product path

The old APIs of Button, Chip and ActionMenuItem stay unchanged. Component content is declared as lightweight Flex parts, calling `layout_engine::parts`; its main-axis distribution, shrink and alignment reuse the retained Flex solver functions. Parts have no `StableNodeId` and create no wrapper, component lifecycle or second tree.

`UiWorld` writes `TextContent`, `LeadingContent`, `TrailingContent`, `Hint` and `Spinner` into `LayoutResult.parts` in the same layout publication. Text fragments use the real `TextContent` boxes. Scene component geometry only reads these parts and attaches draw data such as color, text and icons. A compatibility query during publication calls the same part solver.

A text-only Button or Chip keeps its original two parts (text and content) and adds no retained node or part. A change in loading, content alignment, a menu hint or an icon placeholder invalidates the layout input; hover, disabled color and spinner phase keep the layout result. A very narrow content box clips the part extents so an icon or hint cannot produce a negative width.

When a control hands its content to parts, it keeps only one part declaration: the intrinsic measure takes their width and spacing other than text (`parts::chrome_extent`), the paragraph budget is the available width minus the same (`parts::text_budget`), placement solves them with Flex, and drawing reads the published result. Checkbox migrated by this rule: the indicator box and the label are the `Indicator` / `TextContent` parts (the indicator box is the same kind of part as a radio ring, #388), and a Checkbox is still one entity with three parts (text, content, indicator box); checking and hover change drawing only, zero layout. The indicator box takes a square from the content box; when the content box is shorter than the indicator box the label moves left with it and no longer leaves the old fixed width. A Switch's text is not node text: the label and hint draw inside parts, one row is the track and a text column, the text column is a nested Flex column, and the height of a switch with a hint comes from measuring that declaration, so styles no longer write `min_height`. The track and the gap do not appear in the switch's own style, and a theme change that alters them still remeasures the switch (`visual_parts_read_theme`). The dot of StatusBadge / ValidationMessage works the same way: the dot is centered in its cell, the cell width and gap read the theme spacing, and padding is only the control's own padding. The intrinsic measure lets text claim width only after subtracting these parts, consistent with the paragraph budget: a stretch of text filling the available width used to make a Button, Checkbox or status dot with an icon overflow the available width by the parts' width.

A control whose label was cleared (Button, Chip, Checkbox and any box that carries its own text) gives back the old text measure, identical to the same control without text under cold layout. A box that had no text no longer enters text work with an old measure left behind, and a Button whose label was cleared keeps its original width.

The page has already moved on to [InlineContent](https://github.com/sena-nana/NanaUI/blob/main/docs/reference/inline-content.md): Text/Button/Chip/ActionMenuItem accept canonical content, ordinary retained children mix through nana-text object placement, and typed fragments carry a source range; advanced control text reuses Runtime retained layout, and atomic Text children draw independently. The compatibility label/icon fields of `StandardVisual` remain; the fallback label/note/detail of ListItem have migrated to Foundation's TextContent/Note/Detail parts, reusing Flex distribution and RTL placement; leading/content/trailing remain ordinary retained slots that read existing child placements. SidebarRow and FileTab reuse this path; a plain label does not measure note/detail separately. The remaining components and the full chrome/content split continue to migrate per the table below.

## mini-layout audit

The classification follows #205: **1** should be expressed by Flex/Grid/Inline/Overlay; **2** should be expressed by Layout Part/Fragment; **3** component semantic geometry (interaction, data rows, text editing); **4** non-box visual geometry (charts, paths, canvases). Only 1/2 migrate; 3/4 keep their domain algorithms and their outer boxes still read `LayoutResult`. The table covers every branch of `UiWorld::derive_component_geometry` (source checked item by item on 2026-10-29).

## Content part decisions (#388)

Several items were kept as they were during the #205 migration and left to be decided; here is what #388 decided:

- **The Checkbox indicator box is `Indicator`.** It is the same kind of part as the SelectionOption radio ring: a Checkbox publishes the three parts `TextContent`, `ComponentContent` and `Indicator` and no longer has a `LeadingContent`. The `indicator` of `ComponentGeometry::Checkbox` reads this part; hit testing and accessibility read the whole control box, which encloses the indicator box. Gate: `issue388_a_checkbox_indicator_is_the_indicator_part` (labelled and empty label: the part kind, the drawn indicator box equals the part, the indicator box center hits this Checkbox, the accessibility box encloses it).
- **RTL mirroring.** Under `direction: rtl` (its own or inherited), the parts of Checkbox, Switch, radio ring (SelectionOption's ring and icon), status dot (StatusBadge / ValidationMessage), Toast and menu triggers lay out by logical direction: the indicator box or mark at the inline start (the right), the close target at the inline end (the left), and the Switch's `End` end at the inline end, as is the thumb's "on" end. `UiWorld::right_to_left` reads `direction` from the computed style, and `start_row_parts`, `selection_option_row`, `switch_parts` (`SwitchInputs::reverse`) and `toast_parts` (`ToastInputs::reverse`) reverse the same row Flex solve; an assembled Toast's mark band (the #385 leading parts) is `LeadingParts { end: true }` at the right end of the content box, while child boxes still start at the content box start with the band width subtracted (`LeadingParts::offset`). Scene reverses the travel by the node's `direction` when drawing the Switch thumb and the loading spinner. The checkmark, the close cross and the status marks themselves are not mirrored. Measurement is direction-independent; a direction change only re-places. EmptyState and Card leading parts run down the column and are unaffected. Gate: `issue388_controls_mirror_their_parts_under_rtl` (11 controls: LTR and RTL layout of the same page, every part the mirror inside the control's own box, and an assembled Toast's children as well; the page direction switches incrementally LTR→RTL→LTR→RTL with `assert_matches_cold` at each step); Scene's `issue388_a_right_to_left_switch_thumb_is_the_mirror_image` (the thumb at 0, 0.25 and 1 progress and the spinner mirror LTR).
- **A Switch label counts toward the intrinsic width.** The label and hint are the visual's own text, not node text, and `UiWorld::switch_inputs` measures both single-line widths at the drawing font size and weight and takes the wider one (`SwitchInputs::text`); measure puts it into `VisualContent::text` beside the track and gap like node text, capped by the available width minus the track and gap. A shrink-wrapped Switch (`fit-content` / `max-content`, or inside a container sized by content) therefore no longer clips or overflows the label; when the row is narrower than the label the Switch stays in the row and the label truncates at the part width. This matches Checkbox (whose label is node text and already counted). A change in the label or hint text, not merely its presence, invalidates layout. A Switch with a label defaults to `Fill` width and is unaffected. Gate: `issue388_a_switch_label_counts_toward_its_width` (short/long labels with and without a hint: the content box equals track + gap + the wider text, the label part fits the label, the next sibling follows it; no overflow in a 160px row; incremental label and hint changes match cold layout).
- **A bare toast's long title wraps, at most twice, then ellipsizes.** One line loses the meaning of a medium-length title, and two lines cap the toast's height. A bare Toast's title (node text) is shaped to the title part width with `wrap`, `ellipsis` and `max_lines` of 2 (the component's own rule, just as the Card title is fixed to one line; the recipe's `title_max_lines` governs an assembled toast, defaults to 1 and is unchanged); the Card title is still one line. The title part height is the recipe's title font size plus the height after the first shaped line (`UiWorld::toast_inputs` reads the retained `TextLayout`), the description part moves down with it, measurement derives the height from the same `ToastInputs::chrome`, and the toast grows with the second line; a one-line title is exactly as before. Gate: `issue388_a_bare_toast_title_wraps_to_two_lines_then_ellipsis` (short, medium and long titles in a 300px column, with and without a description: the short title is one line and the part height equals the recipe font size; the medium title is two lines without ellipsis, the long one is two lines ending with an ellipsis, the title part height equals the font size plus the second line, the shaped width does not exceed the part, the toast is taller than at one line, and the description sits under the title inside the box; incremental title and description changes match cold layout).

## Verification entry points

- `cargo test --locked -p nana-ui-runtime --lib issue205`: parts agree with the draw projection, hint/loading updates, a11y, hover zero layout, 1k/10k single entities and retained part counts; the Checkbox parts, measure and budget against cold layout; an emptied label matches cold layout; menu space and chrome clipping follow the clip chain.
- `cargo test --locked -p nana-ui-runtime --lib issue384`: Range (then Progress, ModalFrame) parts agree with drawing and with cold layout, context switching, 1k/10k entity counts; every drag step on Range is zero layout.
- `cargo test --locked -p nana-ui-runtime --lib issue388`: the four #388 decisions, see the section above.
- `cargo test --locked -p nana-ui-runtime --lib issue385`: the leading parts of EmptyState, Card and an assembled Toast match cold layout under author padding, theme switching and part visibility; padding is only the declared one, parts start at the content box start, and child nodes follow the band.
- `cargo test --locked -p nana-ui-runtime --lib issue199`: 1k real components switching across contexts / normal flow and detached flow keep state, focus and resource identity.
- `cargo test --locked -p nana-ui-devtools --features runtime-agent --test devtools_pixels component_pixels`: component pixels and hover on a real GPU; with `NANA_COMPONENT_REQUIRE_GPU=1` a missing GPU must fail.

The Card title reuses Runtime's retained paragraph with its own single-line glyph budget and font size/weight; those text styles do not inherit into the body. The Header baseline shares one part with the intrinsic baseline of every context, and the title height is reserved once by the band. The spinner phase is paint-only; overflow glyphs of a narrow title are clipped to the Header and cannot take the spinner gap.

The CPU p95 and allocator/RSS historical ratios need before/after reports on a fixed machine. The entity-count and part-count gates prove structural cost only and do not replace #188's CPU ≤5% / memory ≤8% ratio acceptance.
