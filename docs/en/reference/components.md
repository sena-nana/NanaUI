# Controls

You mount ready-made controls onto the tree. Do not paint every button yourself. The Rust entry point is `nana_ui::runtime`.

```rust
let (_, save) = cx.mount_view_root(document_id, || {
    let save = entity_ref::<Button>();
    let view = button("Save").entity_ref(save).on(|_: &Activate| {
        // Your own save logic
    });
    with_refs(view, save)
})?;
```

For look and sizing see [Look](https://github.com/sena-nana/NanaUI/blob/main/docs/reference/look.md).

## Contents

**Actions and input.** `Button`, `IconButton`, `TextInput`, `TextArea`, `NumberInput`, `ScrubField`, `Checkbox`, `Switch`, `RangeField`, `RangeSpanField`, `CurveField`, `Select`, `Dropdown`, `SearchDropdown`, `SegmentedControl`, `Tabs`, `XYPad`, `ColorField`, `PathField`, `DatePicker`. `RangeField` draws the current value and unit next to the track by default. `.show_value(false)` leaves only the track. A screen reader still reads the value. `.show_label(false)` does not draw the label. The track fills the control. The label is still the accessible name. `.rail(thickness)` draws a single thin rail across the control, the dot appears only while the control has focus, and the control height is the hit area. `.track_gradient(stops)` draws the track as a gradient bar (for color scales such as hue or opacity): no fill, the dot becomes a contrasting-color ring, and the accessibility semantics do not change. `.value_thumb(true)` writes the reading into a wide capsule slider (dragging on the capsule does not jump the value; click or Enter to type), `.show_bounds(true)` writes the minimum and the maximum with its unit at the two ends of the track, and `.default_value(Some(value))` puts a restore-default button at the end of the row; holding Alt (Option) while dragging multiplies the change per pixel by 0.1, see "Value-thumb slider" in [RangeField](https://github.com/sena-nana/NanaUI/blob/main/docs/components/range-field.md). `.surface(XYPadSurface::Picture)` on `XYPad` makes the pad's own background color and background layer the picture, draws no cross axes, and marks the value with the same contrasting-color ring; the HSV square and hue bar of `ColorField` are exactly these two. `RangeSpanField` (`<RangeSpan>`) is a range enclosed by two sliders, and can be vertical (minimum at the bottom); each slider is its own focus stop and a screen-reader `Slider`. `indicator` is a live value on the track that does not snap and takes no input; changing only it is one paint update. The ends of the track are inset from the node edge by `range_span_track_inset(size)`; custom drawing alongside aligns to it. `CurveField` (`<Curve>`) is a polyline in a unit square: the points sit at fixed, evenly spaced horizontal positions and can only be dragged up and down; each point is a focus stop and a vertical screen-reader `Slider` (the value reads as a percentage), the left and right arrows move between points and up and down change the height; `ends` gives the fixed heights at the two ends. The four sides of the square are inset by `curve_plot_inset(size)`.

**Layout and text primitives.** `Text`, `Stack` (presets such as `row` / `column` / `bar` / `spacer` / `layers` / `overlay_layer`), `Divider`, `IconGlyph`, `ScrollView`. `Stack::spacer()` is zero-width flex-grow. It pushes the siblings after it to the end of the row. `Stack::layers()` is a stack of layers: the children share one area and align independently, the same as ZStack / Box. `Stack::overlay_layer()` is a layer that fills the positioned parent. It leaves flow. It does not hit. It clips. Use it as the container for stage HUDs and danmaku. The node pool is still mounted by your application. `Divider` defaults to `Fill` on the cross axis + `align_self: Stretch`. It is still visible inside a column with `align_items: Start`.

**Tables and trees.** `Table` / `TableRow` / `TableCell`, `TreeView`, `ReorderList`. Columns can be `sortable(true)`. Activating a header goes through `VirtualTableLayout::toggle_sort` (ascending → descending → off). `move_column` reorders columns. **Sorting itself is still the application's job.** Only you know how your data compares.

**Display.** `Card`, `List` / `ListItem`, `FormField`, `EmptyState`, `Progress`, `Skeleton`, `Spinner`, `StatusBadge`, `Chip`, `Avatar`, `PathText`, `Tooltip`, `ValidationMessage`, `QrCode`, `ImageViewer`, `NativeMarkdown`, `CalendarHeatmap`, `Chart`, `GraphCanvas`, `GraphMinimap`.

**Overlays.** `Dialog`, `ConfirmDialog`, `Drawer`, `Popover`, `ActionMenu`, `ContextMenu`, `CommandPalette`. The in-app menu bar `AppMenuBar` pops up its menu panel itself, without going through `OverlayHost`, see [AppMenuBar](https://github.com/sena-nana/NanaUI/blob/main/docs/components/app-menu-bar.md). The framework places overlays inside the window. Near an edge they are pulled into the viewport. Do not build your own layer with `position: fixed`. The triggers of `Popover` / `ActionMenu` support text (`trigger`) and icon (`trigger_icon`). An icon trigger renders as a 28×28 square button. The icon is geometrically centered in the button. The accessible name comes from the `trigger_icon` label. Do not use a text trigger for a bare symbol (such as `+`). For a trigger like "icon + text + count" (favorites 1800), use the view's `.trigger(view)` named slot (`Popover::trigger_content(id)`). That content is the trigger's own children. It lays out horizontally inside the trigger's shell. It is still shown while the panel is closed. It does not count as a panel item. The `trigger` text is still the accessible name. **The trigger is still the popover itself.** Pressing, focus, Enter / Space and the panel's anchor all belong to it. So this content is display only. Do not put pressable controls inside it. When the panel closes because its trigger was pressed, because of Escape, because of a press outside, or because the application wrote `open = false`, focus returns to the trigger if it was still on an item in the panel. Trade-off: this was not made "any element with `anchor: NodeRef` opens a popover". That would make the panel follow another node's box. The layout would then need one more cross-node dependency (the panel stays where it was when the anchor moves and the popover is not laid out again). It would also need extra wiring for opening, focus return and outside-press detection. The slot lets the anchor, hit testing, keyboard and closing reuse the popover's existing single path. The cost is that the trigger's shell (the default Subtle background, the control height) is supplied by the popover. `Popover::bare_trigger(true)` (`ActionMenu` forwards it too) removes the resting background and border, while hover, press and open still lay down a wash. Omit it to keep the light background and border. The pop-up surface is viewport-fixed. **It does not enter the parent's isolation group.** A menu inside a card paints above later sibling cards. Overlaps hit in the same order. The application does not have to raise `z_index` on the whole card. The overflow clip of the panel it lives in cannot clip it either. Card surface and panel content are one layer. It covers the trigger and content painted later on the page (including later siblings with a higher `z_index`). A press on blank card surface stays in the panel. It does not fall through. It does not toggle the panel either. The pop-up layers of `Popover` / `ActionMenu` / `HoverCard` are anchored to **where the trigger is shown** (the box after ancestor scrolling and transforms). When one side of `placement` does not fit and the opposite side does, it flips to the opposite side. Then it is pulled into the viewport along both axes. It only covers the trigger when neither side fits. After opening, scrolling the page leaves the pop-up where it was until the next layout. `DesktopShell` has two `OverlayHost` layers. `overlay` holds dialogs. `status` holds toasts. Toasts can still show while a confirm dialog is open. The title row of `Dialog` / `Drawer` can take a piece of view in place of the title text: `.title_content(view)` (`ModalSlots::title_content`), such as a name followed by a status badge; it stands where the title text would be, vertically centered in the row, the title text is no longer drawn, and `title` is still the accessible name (see [Dialog](https://github.com/sena-nana/NanaUI/blob/main/docs/components/dialog.md#标题内容)). The card shape of `Dialog` / `ConfirmDialog` can be painted by the application itself: `.surface_painter(painter)` records once above the scrim and below the card text and slots in card coordinates, and `PaintContext::modal_sections` gives the positions of the title row, title block, body and footer; position, sections and motion still belong to the theme recipe (see [Dialog](https://github.com/sena-nana/NanaUI/blob/main/docs/components/dialog.md#自己画卡面)). While a modal panel (dialog, drawer) is open, its surface takes every press that lands on it. The rule by which the drag handles of sidebars, splitters and the Dock below grab a press through a "few pixels of tolerance" only applies to handles not covered by the modal. The cursor does not turn into a drag cursor over the panel either.

Leaf composite controls such as `Chip`, `ColorField`, `SizeField`, `PathField` and `FileTab` rebuild their children themselves the moment you write props. You do not need to remember `assemble_*` again. `Shell` / `Workspace` / `Dock` / `SplitPane` / `PaneSection` do not follow this. They coordinate the application's own slots, and they are not cheap. Hanging them on every write would break the dirty-frame contract of "no change, no dirt". These still call the corresponding `assemble_*` explicitly once their slots are assembled.

The confirm / cancel buttons of `ConfirmDialog` are built by `AppContext::assemble_confirm_dialog(dialog)` and wired to `ConfirmIntent`. You do not need to make two buttons yourself and stitch the slots. Override the button text with `confirm_label` / `cancel_label`. `danger(true)` puts the confirm button in the danger color and gives the title a dangerous tone (the same tone as `Dialog::danger`). When you need a secondary action, a close button, custom body text, or content at the left end of the action row (`.footer`, such as a "Do not ask again" switch), use the same-named slot on the view or assemble it yourself with `set_confirm_slots`. In that case `assemble_confirm_dialog` does not overwrite slots you already set.

`ContextMenu` likewise hangs under `OverlayHost` and is opened with `activate_overlay`. The framework handles Escape and outside-press dismissal with Menu semantics. The application no longer builds its own outside-press detection. A framework-driven dismissal syncs the component's own `open` and emits `ContextMenuEvent::Dismiss`. It goes through the same receipt as dismissing on a selected item. The application does not have to reconcile two states afterwards.

**A menu built from components.** `ContextMenu`'s rows are data (`ContextMenuItem`). To put content of your own in a menu, use `AnchoredActionMenu`: a menu surface hung from a point whose children are the menu, laid out in a column, and may be any components: `ActionMenuItem` commands, a `Divider`, a header of the application's own, a scroll view, a text field. It hangs under `OverlayHost` and opens with `activate_overlay` like `ContextMenu`, with Menu semantics: it takes the pointer, a press outside or Escape closes it, and Tab stays inside. The arrow keys, Home and End walk every focusable thing in it in order (not only the Tab stops), wrapping at both ends; while focus is in a text field inside it the arrows belong to the field. Choosing an `ActionMenuItem` in it closes the menu; a row with `ActionMenuItem::keep_open(true)` does not (a level to step into, a state the menu keeps showing); other controls (`ListItem`, `Switch`) leave it open. When the framework closes it, it writes `open = false` and emits `AnchoredMenuDismissed`; the application writing `open = false` itself emits nothing. `AppContext::dismiss_anchored_menu` closes it the same way. Submenus are not built in: to replace one level with another, make the content a view that follows state and give the row that steps in `keep_open`.

`Toast::place_in(viewport, PopoverAlignment::Center, max_width, PanelInsets { .. })` pins a toast into the free area using the same reservation contract as `Panel::viewport`. `align` decides its distribution across the remaining width. `max_width` caps it. The height is still decided by the content, and it sticks to the reserved bottom edge. `viewport` is the box of the positioning host itself. An unplaced toast still fills its row. A placed toast keeps its own width. The free area is supplied by the application. Only the application knows which panels it has opened.

`Toast::timeout(Duration)` makes a toast emit one `ToastDismissed` after it has been mounted that long, the same event as pressing the close button. The timer starts once per toast, wakes the host once at expiry, and does not advance frame by frame. Omit it and the toast waits for the user to close it. The framework never removes a toast itself; the application deletes it from the list when it receives the event.

`AppContext::assemble_toast(toast)` permanently turns a toast into a composite form made of children: the title and description wrap at the recipe's line count, plus a progress bar (`Toast::progress`, determinate or indeterminate), one action button (`Toast::action`, emits `ToastAction`), a pressable close button (when `dismissible`, emits `ToastDismissed`) and `Toast::icon` replacing the tinted glyph. These appear only after assembly; a bare `Toast` is still the painted leaf it was. A composite toast is as wide as its content, and at least the recipe's `progress.min_width` while progress shows; the timer pauses while the pointer hovers it or focus is inside, and continues with the remaining time after they leave. See [Toast](https://github.com/sena-nana/NanaUI/blob/main/docs/components/toast.md).

Use [ToastStack](https://github.com/sena-nana/NanaUI/blob/main/docs/components/toast-stack.md) for the notification corner. `push_toast` assembles a toast and puts it in as the newest one, measuring height first, then deciding which ones to show by `max_visible` and height, queueing the rest; `remove_toast` lets the on-screen one play its exit in place before removing it and closes the gap; `clear_toasts` removes them all. `ToastStack::place_in` uses the same reservation contract as `Toast::place_in`, plus a `max_height`. The stack itself does not hit, and gaps fall through to the stage below. When the application puts the stack above the modal layer (the modal card's `z_index` is 1000), the toasts in the stack stay pressable while a modal is open, they do not count as a press outside the modal, and focus and Tab stay in the modal.

Notifications in multi-window applications use `nana_ui::notices`. `NoticeCenter<K, A>` exists once and holds every notice: keyed ones with a business key `K` replace in place, and keyless messages with the same text do not repeat within `repeat_window`. When the total exceeds `max`, ordinary messages give way first; running tasks and their results are not lost. Each notice remembers its source window (`NoticeSource`), landing in the focused window at creation, otherwise in turn the main window, the preferred window given to `set_visible`, and the most recently active window. When the source is hidden or closed the notice migrates, preferring the main window; with no visible window it is parked and does not count time. Migration rebuilds the Toast, the old window's callbacks become invalid, and content already announced is not read again. Each window mounts a `NoticeHost` (a `ToastStack` inside), and each frame calls `sync(cx, host, window, width, height, placement)` to project; it returns true only when the projection changed. Actions and dismissals come back from `drain()` with their source. `set_shown_elsewhere(keys)` pauses projection of those keys, leaving them for elsewhere.

`Spinner` turns itself. After mounting, an infinite Motion IR timeline drives the rotation phase. The host does not feed the phase frame by frame. To stop it, unmount or park the node.

`Panel` is a non-modal task panel. Mount it as a direct child of a separate `OverlayHost`. Showing it and its exit animation both go through `activate_overlay` / `dismiss_overlay`. A panel uses the Card surface and named Region accessibility semantics. Only the card surface hits. The outside stage and the normal Tab order stay usable. Do not pass off a Menu or a Dialog as a non-modal panel. The visible title, back/close buttons and content are assembled by the application as ordinary children. Use `ScrollView` for long content. The close button calls `dismiss_overlay`. Do not delete the node directly.

`Panel::viewport(viewport, PanelEdge::Right, width, PanelInsets { .. })` constrains width and height to the viewport left after the application has reserved space for a title bar, bottom bar and so on. `Panel::bounds` gives the rectangle of the same layout contract. `viewport` uses logical coordinates relative to the host. The host must cover the viewport passed in. `Panel::style` plugs into existing styles. There is no second theme or painter. Each coexisting panel uses its own host. Layer order is controlled by the existing `z_index`. A confirm dialog should sit above task panels.

Activation focuses the first valid child control by default. To bring back a pinned panel, use `focus_on_open(false)` to keep the current focus. On close, a valid entry point is restored only if focus is still inside the panel. Hidden, unmounted or invalid entry points are not focused. `focus_first_in(document, root)` focuses a subtree using Runtime's Tab candidate rules. Applications that need to go back to business details first take over Escape with `close_on_escape(false)` and then close the panel at the routing root. Business navigation, pinning preferences, and which panel collapses in a narrow window are owned by the application.

Only one direct child panel is active per host. The other subtrees keep their content and editing state. But they are not painted. They do not hit. They do not join Tab. No parking is needed. To pin / unpin the same content, use `transfer_panel(panel, source_host, destination_host)` to hand it over atomically to another host in the same document. Nodes, focus and animation are kept. Do not dismiss and then reparent. The destination's old panel becomes inactive. Both hosts receive `OverlayChanged`. No `OverlayClosing` is sent. A panel that is exiting cannot be transferred.

An inactive overlay and a closed menu are structural hiding. `ComputedStyle::box_visible` is inherited down the whole subtree. A child cannot rejoin painting with CSS `visibility: visible`. Ordinary CSS `visibility: hidden` still lets a child override explicitly. Closing a retained Panel does not reset the `ScrollView` scroll offset. Reopening the same node with unchanged content and viewport restores the original position. When the content or viewport changes, normal range constraints still apply. Regression tests for `nana-ui-scene`'s `RuntimeDocument` check closing, reopening and switching through actual incremental scene primitives. They also verify scroll offset after close and reopen around a full layout refresh. They do not only assert the world's visibility field.

The user's close gestures (Escape, press outside, close affordance) first emit `DialogCloseRequested { trigger }` on the `Dialog`, `ConfirmDialog` or `Drawer` itself, and then `close_policy` decides whether the framework closes it. A gesture the policy does not allow only emits the request and the overlay stays. `DialogClosePolicy::requests_only()` makes the framework close none of them, leaving opening and closing entirely to the application. The application does not have to poll the accessibility tree to discover "the dialog was closed by the framework".

The keyboard conventions for overlays (guarded by tests on the real key path: `enter_activates_the_focused_default_action_and_escape_closes_the_dialog`, `enter_opens_and_escape_closes_a_popover_from_the_keyboard`):

- **Escape** closes the topmost overlay: dialogs, confirm dialogs and drawers follow `close_policy` (allowed by default; emits `DialogCloseRequested { trigger: Escape }` first); `Popover` / `ActionMenu` follow `close_on_escape` (on by default), and after closing, focus returns to the trigger if it was in the panel. When a dropdown or completion popup is still open inside the panel, Escape closes that layer first.
- **Enter** activates the focused action; there is no separate notion of a "default button": when a modal opens, focus lands on `initial_focus` (default `FirstAction`, which is "Cancel" in a confirm dialog, so a stray Enter does not run a destructive action). To have Enter confirm directly, write `.initial_focus(ModalInitialFocus::Target(confirm button))`. On a `Popover` trigger, Enter / Space toggles the panel.

`Dialog`, `ConfirmDialog` and `Drawer` can also declare opening and closing: `.open(..)` / `.model(signal)`; under `OverlayHost` these are `activate_overlay` / `dismiss_overlay`, and opening and closing done by the host emits `DialogToggled` and writes back `open` (see [Dialog](https://github.com/sena-nana/NanaUI/blob/main/docs/components/dialog.md#声明式开合)).

`dismiss_overlay` closes interaction and restores focus first. Then it keeps painting the menu / dialog until the exit animation ends. The host syncs its business open state through `OverlayClosing { root }`. It handles final release through `OverlayChanged { active: None }`. A queued close notification should be consumed before the next projection, and the overlay identity should be checked to avoid overwriting a fast reopen. During exit, the parent-child relation and the node in `DesktopShell.overlays` are kept. Calling `remove_view` directly releases at once and skips the exit animation.

**Shell.** `AppShell` / `DesktopShell`, `AppTitleBar`, `Toolbar`, `StatusBar`, `MediaTransportBar`, `Workspace`, `SidebarFrame` / `SidebarSection` / `SidebarRow`, settings rows and the settings page, `Dock`, `SplitPane`, `PaneChrome`. The shell is the generic desktop structure. What goes in each region is decided by the application. See [Workspace](https://github.com/sena-nana/NanaUI/blob/main/docs/reference/workspace.md). Whether the primary region has rounded corners (the "Workspace corners" appearance setting) is written on `DesktopShell::workspace_corners`. When the shell assembles, it hands this to the `Workspace` it builds. Do not modify the `Workspace` node the framework built. The next assembly overwrites it with the value on the shell.

`SettingsRow::stack_below(480.0)` optionally enables responsive arrangement based on **the row's actual layout width**. Below the threshold the label and the control stack; at or above it they share a row. Off by default. `stacked(true)` always stacks. An invalid threshold counts as off. The control node is not rebuilt. Width changes are handled by Runtime layout reflow. The application does not need to scan rows every frame.

The settings row label gives the control placed in it its accessible name. When `SettingsRow` assembles (`settings_row(..).control(..)` in views, `mount_settings_leaf_row`, and the rows of `AppearanceSection`) it links the two with `MutationQueue::set_labelled_by(control, label node)`. When the control has a non-empty name of its own, that one is used (`switch("Mute")`). When it does not (`switch("")`, segmented controls, sliders, dropdown selects) the row label is used. When the row label changes, the control's accessibility node is reprojected along with it. This link belongs to the composite control. It lives in `UiWorld`. It is not part of the control's `AccessibilityState`. So a control reprojecting its own state does not wash it out. When either end is destroyed the link goes with it. `Select` therefore no longer takes its displayed option as its accessible name. With nobody naming it, it is still named by the displayed text. The displayed option is its value (`value`).

`SettingsRow::label_mark` and `SettingsRow::label_accessory` are application nodes on the same line after the label: `label_mark` sits immediately after the label text before the help button (category marks), while `label_accessory` follows the help button (status pills, reset actions). Assembly wraps the label in a row only when a mark, help button, or accessory is present; the label narrows and elides first, the mark and accessory keep their widths; the row's accessible name is still the label. `AppContext::flash_settings_row(row)` flashes a row, for when the application has brought the user to it: an `AccentSoft` tint that takes no layout and no pointer sits under the row, extended left and right by one list item inset, holds on the presentation layer as `MotionRole::Attention` and then fades out, and the node is removed when it ends; with reduced motion it stays at full color for the same duration. See [SettingsRow](https://github.com/sena-nana/NanaUI/blob/main/docs/components/settings-row.md).

Outside settings rows, any element in a view can declare the same kind of link: `.labelled_by(title)` (template `labelled_by={caption}`, in `.vue` `labelled-by="caption"`). `title` is the `NodeRef` of that text, a node id, or a closure selecting it. Write it before the control, after it, or in another piece of view. When the title is rebuilt (inside `when`) the link follows to the new node. Dropdowns, sliders and switches with an empty label that have a field caption beside them are named this way, with no scanning of the document after mounting. With no visible title, `Select` writes its own `label` (`aria-label`, not drawn), and `RangeField` writes `label` plus `show_label(false)`.

Controls can also carry an explicit accessible name and description, written the same way as `Button::accessible_name`: `.accessible_name(name)` (`aria-label`) and `.accessible_description(description)` (`aria-description`, read after the name, not drawn). An empty string counts as not written.

| Control | Name | Description |
| --- | --- | --- |
| `Switch` | `accessible_name` beats the visible `label`; a switch with an empty label is named by it | `accessible_description` |
| `RangeField` (slider) | `accessible_name` beats `label` and does not change the visible text | `accessible_description` |
| `Select` | `accessible_name` writes `label` itself (it is never drawn) | `accessible_description` |
| `Dropdown` | `accessible_name` replaces the displayed value as the name; the displayed value is still the value | `accessible_description` |
| `TextInput` / `TextArea` | `accessible_name` writes `label` itself (it is never drawn); the placeholder never serves as the name | `accessible_description` |
| `RichTextEditor` | `accessible_name`; when not written, it is named by `.labelled_by(..)` or another link | `accessible_description` |

The same-named attributes are available in templates and `.vue`: `accessible_name` / `accessible_description` on `Switch` and `Slider`, and `accessible_description` on `TextInput`, `TextArea` and `Select` (the name is still `label`).

`mount_settings_leaf_row` keeps the label, hint and control slots. A row with no hint initially can show one later through `update_component(row, |row, _| row.hint = Some(...))`. Setting `None` hides it. `assemble_appearance_section` keeps the application's `stack_below` and `stacked` when it refreshes existing rows.


Some families need a Cargo feature (`calendar`, `charts`, `graph-canvas`, `rich-text` and so on). See [Application API](https://github.com/sena-nana/NanaUI/blob/main/docs/reference/application-api.md). These features forward to `nana-ui-runtime` and `nana-ui-scene`. They control the corresponding implementation, geometry projection and public exports. `components` enables every optional control family. A minimal host picks what it needs.

`DatePicker` is a month calendar grid. It is composed of existing controls (header icon buttons + day buttons). `assemble_date_picker` builds and reuses these 6×7 buttons. Changing month only swaps labels, without rebuilding. Selection emits `DateChanged`. Changing month emits `DateCursorMoved`. Dates outside `range` and outside the current month are not selectable. **The month title is supplied by the application** (`month_label`). Month names are locale-dependent. The framework does not ship locale data. The date type is `nana_ui_core::CivilDate`. It has only year, month and day. It is not a date-time library.

`Toolbar` / `StatusBar` are two horizontal bar containers. The application puts content in. Compared with a bare `Stack::bar` they add the shell surface and **accessibility roles**. A screen reader announces the toolbar as a group of controls. It announces the status bar as a live status region. A plain layout box cannot express this. `chrome(false)` is for a parent container that already has its own surface.

When the two bars do not fit, they tighten first and overflow second (Dynamic Layout, see "Dynamic Layout" in [Layout](https://github.com/sena-nana/NanaUI/blob/main/docs/reference/layout.md)): the bar's own gap tightens to a quarter first, then the left and right padding declared by `Button` and `Chip` tightens (each to a third); only when all of that is used up does it overflow or hand over to shrink. This comes from `adaptation: Some(AdaptationProfile::strip())` in the bar style; `Button` / `Chip` carry `AdaptationProfile::control()` by default, which is only a declaration, and containers that do not solve it (ordinary `Stack`, rows, columns, Dock, SplitPane) neither read it nor pay for it. Any container that writes `solve_overflow: true` can solve this way; to keep a button from tightening, set its `adaptation` to `AdaptationProfile::RIGID`. `StatusBadge` does not declare it: the status dot is drawn in the left padding, and tightening would push the text onto the dot.

Drag and drop: `set_drop_target(entity, DropAccepts::files())` registers what a node accepts. `drop_target_at(document, x, y, kind)` answers which node at a point, innermost first, accepts that payload (matching by layout box, no clickability required). **The framework only answers where it landed.** What happens after the drop is still the application's. Same as `SecondaryPress`. Dragging in Tab / Dock / `ReorderList` moves the framework's own structure. It still follows its own contracts.

Hover show and hide: give a node a `PointerHoverChanged` handler and it receives `hovered: true` when the pointer enters its subtree and `false` when it leaves. Moving between two descendants inside the subtree does not emit again. Only nodes with a handler receive it, from the inside out. `Stack` does not take part in hit testing by default, so the pointer resting on the blank part of a row does not hit it; use `.hittable()` to make the whole row catch hover. The framework only reports enter and leave; which tools to show is the application's business.

Pointer position: give a node a `PointerMoved` handler and it receives `x` and `y` while the pointer moves over its subtree, in that node's own layout coordinates (the border box's top-left is `0, 0`). The nodes that receive it are exactly the ones `PointerHoverChanged` counts as hovered: only nodes with a handler, from the inside out; they still receive it while the pointer rests on a control inside the subtree (a `Popover` trigger, a painted `Stack`). Leaving is reported by `PointerHoverChanged` alone and is not repeated here. While a node holds the pointer's capture (during a drag), it and the listeners around it keep receiving moves, and the coordinates may lie outside the node. Until some node has a handler for it, routing does no extra work.

Dragging: give a node a `PointerDragged` handler and a primary-button press in its subtree that is dragged goes to the innermost node with a handler. A press released before it travels more than 4 px (a finger uses the touch scrolling slop) is still an ordinary press: it focuses, activates and opens a `Popover` exactly as before, and no drag event is emitted. Past the slop it becomes a drag: `Started` first (the press point, with no travel), then one `Moved` per sample (the one that crossed the slop included), `Ended` on release, and `Cancelled` when the pointer is cancelled or the node loses the capture. From `Started` on the node holds the pointer (when the node takes no pointer itself, such as a layout `Stack` without `.hittable()`, the control the press landed on holds it instead), the control the press began on no longer shows its pressed state and its release activates nothing (a `Popover` does not open, a button does not click); focus stays where the press put it. `x` and `y` are the node's own layout coordinates; `dx` and `dy` are the travel from the press point in logical px as the window measures it, so a node that moves with its value does not change them. A press another control already took (a slider, a text caret or selection, a scrollbar) does not become a drag. Keyboard and wheel are unaffected. A finger in a scroll area is offered to the scroll area first: if it can scroll that way it scrolls, and no drag starts. As with `PointerHoverChanged`, a `Stack` needs `.hittable()` to catch the press. The framework only reports where the drag went; what dragging means is the application's business.

Keyboard focus is reported by `FocusWithinChanged`, with the same rules as hover: it receives `focused: true` when focus enters the node's subtree and `false` when it leaves, and moving inside the subtree does not emit again. When a listener is inside `update_component`, the event is delivered after that update finishes. A node with `VisibilitySpec::Hidden` does not join the Tab order, so tools that only appear on hover should be tucked away with `opacity: 0` so Tab can still land on them, then revealed together with hover in `FocusWithinChanged`.

Selection position: `UiWorld::text_selection_bounds(id)` answers the bounding rectangle in the window of the selection in `NativeMarkdown` / `SelectableRichText`, already accounting for ancestor scrolling and transforms, and `None` when there is no selection. Use it to anchor a floating toolbar to the selection: ask after the update that changed the selection returns, and ask again after scrolling. Combine it with `resolve_popover_origin` to decide whether to place it above or below the selection.

`NumberInput::steppers(false)` hides the up and down stepper buttons, their click area and the reserved width; number validation, submission and keyboard arrow keys keep their rules, and the buttons are shown by default.

`SizeField` is a "width × height ▾" sharing one frame: two `NumberInput`s without steppers split the width evenly, and a square `ActionMenu` icon at the right end opens presets; submitting one side or a preset both emit `SizeFieldChanged { value: [f64; 2] }` (`SizeChanged` is already used for layout events). `range` / `step` follow the number field rules, and `SizePreset` provides a name, width and height values and a disabled state, with the width and height values as the item identity. `value`, `presets` and the accessible names of the parts support view binding; writing the same value back from outside keeps the edit draft, selection and undo, and refreshing items keeps the menu identity and focus. Disabling the whole field closes the menu and disables the internal operations.

`ColorField` is a swatch + hex. `assemble_color_field` mounts the HSV picker. Submission emits `ColorChanged`. Dragging emits `ColorInput`. `PathField` is a path + browse button. Browsing only emits `BrowseRequested`. The application opens the system dialog.

### Chip

`Chip` is a compact selectable token (pill). Its identity is `nana.chip`. It is a leaf composite: writing `dismissible` makes `update_component` run `assemble_chip` itself. No second call to remember. `selected` uses the Selected background. Otherwise Subtle.

| Action | Runtime |
| --- | --- |
| Press the body / Enter / Space | `Activate` |
| Press the close button | `ChipDismissed` |
| `disabled` | No events, not focusable |

Closing is a request. The application removes it. A press on close must not also send `Activate` to the Chip. The default accessible name of close is "Remove" (`close_label`). AccessKit: the body is one activatable Button (`selected` maps to the selected state). The close button is another separate focusable Button. It is not a list item.

Compared with `Button`: a Button is an action. It has no token `selected` / `dismissible`. Compared with `StatusBadge`: a Badge only displays. It does not activate. It does not close.

### Marks and groups (view::marks)

The rules for these views when assembled together (content line, heading row, status hierarchy, scroll area) are in [Layout and composition](https://github.com/sena-nana/NanaUI/blob/main/docs/guide/composition.md).

These are not controls but views composed from `Stack` / `Text` / `IconGlyph`, and they only name theme roles and steps:

- `kbd(key)`, `kbd_glyph(icon)`, `chord("Ctrl+B")`, `chord_with(keys, draw_key)`: keycaps and chords; the keycap is drawn by `KeycapPainter` (surface, border, a bottom edge in the strong border color, following light and dark mode), and its height and bottom edge come from `ThemeMetrics::keycap` of the installed theme.
- `tag(text)` / `tag_frame()`: a non-interactive label; use `Chip` for something selectable or closable.
- `callout(icon, tone, text)`: a notice strip colored by `StatusTone`; `.quiet()` is a line of explanation with no background and no horizontal padding, `.trailing(view)` puts an action at the end of the line. See [callout](https://github.com/sena-nana/NanaUI/blob/main/docs/components/callout.md).
- `heading_row(title, tools)` + `heading_tools(tools)`: a heading row. The title gives up width first and the tools keep their width; `.lead(view)` puts an icon before the title. Compact tools (`IconButton::tool`, target `COMPACT_TARGET`) overhang above and below by `heading_overhang()` by default and do not make the heading row taller, `.inline()` keeps them in the row; when the heading is at the top of a scroll area, the scroll area writes `ScrollView::heading_room()`. See [heading_row](https://github.com/sena-nana/NanaUI/blob/main/docs/components/heading-row.md).
- `scroll_foot_fade(height, surface)`: a fade placed on the bottom edge of a scroll area; it takes no input; when the scroll area uses `ScrollView::gutter`, write `.clear_of(gutter)` to give up the scrollbar lane. See [scroll_foot_fade](https://github.com/sena-nana/NanaUI/blob/main/docs/components/scroll-foot-fade.md). When the backdrop is not a solid color, use `ScrollView::edge_fade`.
- `settings_group(title, rows)` + `group_row(view).visible(cond)`: the title above and the card below, with a hairline indented by `CONTENT_INSET` between rows, and a hidden row takes its separator with it. Neither the card nor `group_row` adds left or right padding: put rows on the content line with `group_row_on_line(view)` (that is `group_row(content_line(view))`), and use `group_row` directly for rows that already carry padding. See [settings_group](https://github.com/sena-nana/NanaUI/blob/main/docs/components/settings-group.md).
- `tone_role(tone)`: the color role for a status tone.

`Avatar`'s empty slot is still a Subtle placeholder and draws no initials; an application that wants initials overlays a layer itself.

### ImageViewer

`ImageViewer` is the full-window large-image overlay (`nana.image-viewer`). It draws the scrim, surface, stage and caption row itself. The image is supplied by the application (`HostTexture` / `CustomRender` is painted by the viewer in the stage and clipped to the stage. `Child` is the application's own children). The scrim is the theme's `EffectTokens::media_scrim`. It is dark in light themes too. The image is always placed on dark. The surface and caption row still follow the theme. The built-in value is black 0.99, not the 0.9 often written in CSS. The painter composites in linear light. A black α leaves `1 - α` of the linear luminance behind. 0.99 is about `#1a1a1a` on white (as dark as CSS's 0.9). 0.9 would be the mid gray `#595959`. A custom theme writing this value should derive it the same way. The viewer's **operations are real controls**. The close button is an `IconButton` child built by `assemble_image_viewer`. It is focusable. It has an accessible name (`close_label`, "Close" by default). It has hover and pressed states. Activating it emits `ImageViewerEvent::Close`. These controls always come after every other child of the viewer. So `Child` content filling the whole frame cannot cover them. Hit testing lands on them first too. When content is added after the controls (child changes), the viewer reassembles and moves the controls back to the end. It is a leaf composite. It assembles automatically when the view is built and after every write. A viewer created by hand with `create_component` calls `assemble_image_viewer` itself once. `ImageViewer::geometry(..).close` still gives the close button's position, for the application to keep clear of its own content.

Gallery: `gallery: Option<ImageViewerPosition>` (`.gallery(index, count)`, `index` from 0) tells the viewer where the current image sits in the application's gallery. With more than one image, a surface appears centered at the bottom of the stage. On it are "Previous" and "Next" icon buttons (`previous_label` / `next_label`) and the position "3 / 9". The viewer's accessible value is this position too. The button on the side that has run out is disabled. Activating a button, or pressing ← / → while focus is in the viewer or on its controls, emits `ImageViewerEvent::Previous` / `Next`. At the end the arrow key is not consumed. **Changing the image is the application's job.** On the event, swap the content and write the new position back to `gallery` (whether zoom and pan reset is the application's decision too). With one image or no `gallery` there is no navigation.

### Avatar

`Avatar` is a circular Cover-fit `HostTexture` slot (`nana.avatar` / `<nana-avatar>`, sampling `nana.host-texture`). It does not take part in hit testing by default. It is not focusable. An empty `resource`, a host that clears it, and a load failure all fall back to the Subtle placeholder. It does **not** draw product initials itself. On load failure the host clears `resource` to empty. This does not change the GPU contract that rejects frames for a missing slot. With a `label`, AccessKit reports Image with a name. Without one it is Image with no name. There is no click event. For the difference from `Thumbnail`, see the rustdoc (Cover, circular, fixed edge length).

`HoverCard::trigger_image` only gives a slot name, the same as `Avatar` / `Thumbnail`. When the host texture arrives late or is swapped, register it into the slot again; the component does not change.

### OverlayVisibility

Auto-hiding for media / stage HUDs uses the `OverlayVisibility` **policy object**. `MediaTransportBar::auto_hide(true)` has the runtime drive it (pointer activity within the picture area, keys, and the pointer leaving the picture or the window, plus the runtime clock), emitting `OverlayVisibilityChanged` on each flip; use this for video-only windows, see [MediaTransportBar](https://github.com/sena-nana/NanaUI/blob/main/docs/components/media-transport-bar.md#自动收起). Below is the host-driven form. Hidden after an idle timeout. Revealed after a hover dwell delay. Focus / drag / menu locks (`OverlayLocks`) keep it visible. `active = false` (loading / paused / empty) keeps it visible. It is not a leaf control. It does not go into `register_component`. It does not take part in layout or hit testing. `MediaTransportBar` holds one policy inside. Use `AppContext::sync_overlay_visibility(bar, now, active)` to gather the locks from the world (whether focus / capture is in the bar or its menus, whether any child `Popover.open` is set), advance the policy and return a wakeup. Pointer activity over the picture goes through `reveal_overlay`. Ancestor queries go through the public `AppContext::is_descendant`. **The idle hide does not write the bar's `hidden`.** The bar's own `hidden` (`.visible(..)` / `v-show` in the view) belongs only to the application. It expresses "the whole bar disappears when transport is unavailable". If either one hides it, the bar does not appear (`MediaTransportBar::shown()` reads the combined result, and the node style that gets projected is the same). So a binding re-run (playback progress refreshing) does not bring back a bar that idle-hid. `reveal_overlay` does not reveal a bar the application hid either.

Pointer-following chrome (the main window's title, toolbar and docked Dock) uses this same policy, not a second one. `OverlayVisibility::hidden(config)` starts settled-hidden; the pointer entering calls `set_pointer_inside(now, true)` and leaving calls `conceal(now)`, and coming back within `OverlayVisibilityConfig::leave_grace` does not hide (it absorbs a window-edge leave immediately followed by an enter, and repeated leaves do not postpone an already scheduled moment); the keyboard calls chrome up with `reveal(now)`, which does not change "pointer outside", so chrome still hides once the occupancy ends; occupancy the host decides for itself (a confirm dialog it opened, text editing, a gesture) goes into `OverlayLocks::interaction`; pass `active` as `false` to not hide by the clock. `visible()` is the logical target, and `phase()` gives the `PresencePhase`: fading chrome reports each transition's end to `transition_finished(shown)` (from `PresenceLifecycle::animation_events` or its own animation), and a completion event that does not match the target (the pointer returns during a fade-out) is ignored. Occupancy only preserves or recalls chrome that is still fading; it does not show chrome that has settled hidden again. `MediaTransportBar` shows and hides immediately and settles synchronously on each flip; it has no leave grace.

### MediaTransportBar

The media playback bar (`nana.media-transport-bar`). The framework provides only the basic chrome: play, on-demand progress / live Progress, volume popup, settings `ActionMenu`, fullscreen. The Stacked density puts the current time and total duration at the two ends of the progress bar; Regular / Compact keep a merged reading. Scene controls go into the `leading` / `trailing` / `secondary` slots. Items in the settings menu (theater, separate window, stop playback) go into the `settings` slot (`settings_content`, `.settings(view)` in views). They are put into the settings `ActionMenu` the bar builds itself. When `secondary` has no visible children the second row collapses on its own. The bar becomes a single row. `assemble_media_transport_bar` builds the slots and wires them. `sync_media_transport_bar` writes back the playback state, progress and time reading (`media_clock`: `m:ss` / `h:mm:ss`) and folds an empty second row. It writes only values that changed. `update_component(bar, …)` already syncs after it writes the fields. A playback tick does not need an explicit sync call. Events are `MediaTransportEvent` (PlayPause / Seek / Volume / Fullscreen, plus SeekStarted / SeekEnded and MenuOpened / MenuClosed below). Idle hiding goes through `AppContext::sync_overlay_visibility`. Do not duplicate the descendant / hit-test locks in the application. When the bar's own settings menu and volume popup open and close, the bar emits `MenuOpened` / `MenuClosed` (whether by the trigger, by Escape, by a press outside, or because the settings button was hidden and they closed with it). On receiving it, the host calls `sync_overlay_visibility` once. An open menu holds the bar from then on. After it closes the idle timer restarts from then (otherwise the wakeup would be empty and nothing would wake the host). There is no need to listen for `PopoverToggled` / `PopoverClosed` on the menu node the framework built.

One control has two orthogonal dimensions. A field change takes effect on the next `sync_media_transport_bar`. It is not a second painter:

- `density`: `Regular` (the reading above the progress, with an optional second row), `Compact` (one compact row with the reading beside the progress; settings / fullscreen are hidden by default, `show_settings` / `show_fullscreen` turn them on explicitly, and all three slots stay usable), `Stacked` (the buttons are the same as Compact, while the reading and progress take a full row of their own above, so a narrow surface such as a mini player does not have to squeeze the progress between the buttons) or `Mini` (`.mini()`: a 2px progress rail with a 16px transparent hit band along the top edge, and a row below with play, a mute button `Mute(bool)`, a dotless volume rail, `leading`, the time reading and `trailing`; there is no volume popup. The application no longer moves nodes inside the bar, see [MediaTransportBar](https://github.com/sena-nana/NanaUI/blob/main/docs/components/media-transport-bar.md#mini)).
- `placement`: `Overlay` (Absolute, stuck to the parent's bottom edge, capped by `max_width`, shell not hit) or `Inline` (joins the parent's document flow, its height is the chrome height, it fills the parent horizontally and does not use `max_width`).

The play button shows in every density. `show_play = Some(false)` (`MediaTransportBar::new().show_play(false)`, `.bind(move |bar| bar.show_play = Some(ready.get()))` in views, `<Widget of={MediaTransportBar::new().show_play(false)}>` in templates) hides it. For example while a live room is not ready to play. A hidden button takes no space. It cannot be focused. Focus on it is cleared.

`seekable = false` means on-demand content cannot be dragged right now (still loading, duration unknown). The progress stays in place, grayed out. The application does not have to swap in a different progress control. Live still switches to the progress meter. The progress control's "progress" serves only as the accessible name. It takes no track width.

Compact + Overlay suits a separate window's bottom bar (about 52px for one row plus margins). Compact + Inline suits a shell mini bar. The picture, cover and title are still placed outside the bar by the application. A second `RuntimeDocument` / window gets the same chrome by calling `assemble_media_transport_bar` directly. In markup use `density="compact"` / `density="stacked"`, `placement="inline"`, and the `show-play` / `show-settings` / `show-fullscreen` boolean attributes. Rebinding only updates these settings. Playback state and assembled chrome are kept.

Progress dragging only previews the reading (it follows even when the host is paused and there is no tick). `Seek` is emitted once on release. A cancelled drag emits nothing. Each drag has a `SeekStarted` / `SeekEnded` pair around it (the end comes after `Seek`; on a cancel or a release in place there is only this pair). The host uses it not to write the playback position back during the drag. There is no need to listen for the inner progress control's `RangeInput`. `RangeField`'s own drag start and end is `RangeDragging { dragging }` (keyboard and accessibility steps do not count as dragging). Every keyboard / accessibility step is a commit. Same as the native range. Volume emits `Volume` live while dragging. The bar writes the target into `position` / `volume` before it emits `Seek` / `Volume`. The host's next write is still authoritative. If the host keeps writing the old position before the seek completes, the slider briefly returns to the old position.

`ReorderList` can hold live row children. Pressing on a control in the row (a button and so on that can take focus) and releasing without moving is the control's click; dragging past the drag threshold drags the row. `ReorderItem::tools` marks a subtree that never starts a drag. With no children the row is still painted from the label. A row can be an expanded tree: `ReorderItem::depth` writes the depth, a drag carries the whole subtree, `kind` and `accepts_inside` / `accepts_sibling` (`ReorderAccepts`) declare what can go inside and what can go beside, and the insertion line is indented by the drop depth; Alt plus the arrow keys move between siblings, into the previous sibling, or out of the parent row. Lists with the same `transfer_group` in one document accept drags from each other: the drop is computed by the receiver's rules, the event is emitted on the receiver, and `source` is the value from the original list. `IconButton::with_tooltip` uses the default `TooltipConfig`.

## Interaction

A visible press, input, toggle or selection is wired to real state. Use `on` / `observe`, or `update_component`.

Typical events: `Activate` (buttons), `TextChanged`, `ToggleChanged`, `RangeInput` / `RangeChanged`, `TabsEvent`, `SearchDropdownEvent`, `ContextMenuEvent`. The rustdoc is the authority on signatures. If an `observe` callback of a composite control changes a field that the derived children depend on, call `cx.reassemble()`. After a commit it runs its assembler the same way `update_component` does. Without the call there is no reassembly (for example, a text box being typed into is not written back). `RangeInput` is every visible value (including the drag preview, good for live preview). `RangeChanged` is a commit: the pointer was released with a changed value, a keyboard step, an accessibility `SetValue` or `set_range_value`. A cancelled drag does not commit.

### Who changes state

**Built-in controls drive themselves.** After a user action the control updates its own visible state. Events report "what happened", not "what to do". The application does not need to write the state back to see the change.

| Control | After a user action |
| --- | --- |
| `Checkbox` / `Switch` | Flips `checked` itself and emits `ToggleChanged` |
| `Select` / `Dropdown` / `SearchDropdown` | Writes the selected value itself and collapses the menu |
| `Tabs` | Changes `selected` itself |
| `TreeView` | Applies expand / select itself |
| `Popover` / `ActionMenu` / `ContextMenu` | Toggles `open` itself |
| `SegmentedControl` (including `radio_group()`) | Changes the selection itself on activation and emits `SegmentedSelectionRequested` |

To **veto or rewrite** the user's choice, write the state you want back in the handler (`set_segmented_selection`, `update_component` and so on). Writing the value that is already there again is a no-op. It does not add a commit.

On `SegmentedControl` / `Tabs` the arrow keys only move focus. They do not change the selection (manual activation semantics). The selection follows Enter / Space / click. This is what screen readers expect of a tablist / radiogroup.

`SegmentedControl::fill(true).wrap(true)` turns on adaptive equal division: it wraps by the real label and icon sizes, and every row (the last one included) divides the available width equally; a single item with an overlong label wraps and grows taller. The default `wrap(false)` keeps one row, and Radio and standalone Tabs are unchanged. The layout intent goes into the unified retained measure / placement; the application does not read layout back and change widths.

The right button (button 2) dispatches `SecondaryPress`. From the hit node it walks up to the first node that registered that event. The event carries the hit node and the coordinates. The framework opens no menu. It inserts no default items. Whether a menu pops up and what is in it is decided by the application in the handler (usually a `ContextMenu`). If nobody registered, nothing happens.

The keyboard can ask for a menu too. When the focused node receives the `ContextMenu` key or Shift+F10, the same `SecondaryPress` is dispatched with `keyboard` as `true`. `target` is the focused node, and the coordinates are the center of its box. The rule for walking up to a handler is the same as the right button. The focused control gets this key first: if the application's key policy (`on_key`), a terminal or an editor consumes it, it is not dispatched. A key held down and repeating is not dispatched. When the host has its own gesture of this kind, call `AppContext::secondary_press_focused(document)`. For a menu requested from the keyboard, the application moves focus into it after opening; a right-button menu does not move focus. `SecondaryPress`'s `focus` says which end the key wants focus at: `Some(RovingEdge::Start)` is the first item, `Some(RovingEdge::End)` is the last item, and `None` is the application's choice (usually the first item). The `ContextMenu` key, Shift+F10, `secondary_press_focused` and the right button are all `None`.

**Menu buttons.** A control that pops up a menu declares `has_popup` (`aria-haspopup="menu"`): the fields of `Button`, `IconButton` and `ListItem` (`list_item("Model").has_popup(true)`, template `has_popup={true}`), and custom controls write it into their own `AccessibilityState::has_popup`. A screen reader reports it as a menu button (AccessKit `HasPopup::Menu`). While it has focus, ArrowUp / ArrowDown without a modifier also dispatch `SecondaryPress` with `keyboard: true`, the same as the `ContextMenu` key. When a control uses the arrow keys itself (a slider, a number field) they still belong to the control. Per the WAI-ARIA menu button convention, ArrowDown's `focus` is `Some(RovingEdge::Start)` (focus the first item after opening) and ArrowUp's is `Some(RovingEdge::End)` (the last item). Whether the menu opens, and whether focus lands on that end, is still decided by the application.

**Display-only nodes.** A node whose role would normally carry actions but is only used to show information (a `ListItem`'s `read_only`, `list_item("Hiyori").read_only(true)`) writes `AccessibilityState::display_only`: it is still read with its original role and is not reported as disabled, but it offers no `Click` / `Focus` actions, and those two requests from a screen reader are not forwarded either. It differs from `disabled`: disabled means operable but temporarily unavailable, and it is painted in disabled colors; a display-only node takes its normal colors and takes neither pointer nor focus (`InteractionState` has both flags false).

**Roving focus groups.** After a container declares `.roving_focus(RovingFocusGroup::vertical())` (or `horizontal()`, `.wrap(true)` to join the ends; `AppContext::set_roving_focus_group` is the same declaration), the arrow keys move focus between items while focus is on an item in the group. This is the WAI-ARIA keyboard convention for toolbars and menus.

- Items are the focusable, enabled, reachable nodes under the group, in document order. The nearest group owns an item: nested groups each manage their own items.
- A vertical group uses ArrowUp / ArrowDown, a horizontal group ArrowLeft / ArrowRight (swapped when laid out right to left). Home / End go to the first and last item. Keys on the other axis, and keys with a modifier, do not belong to the group.
- The group only takes keys the focused control lets through. A text box's cursor keys, a slider's steps, and table and tree navigation still belong to them. When the same key is both a vertical group axis and on a menu button, the group takes it first.
- Without wrapping, focus does not move past either end, and the group emits `RovingFocusEdge { edge: RovingEdge::Start | End, item }`. Groups in pop-up layers usually collapse here and give focus back to the control that opened them.
- Every key the group takes is consumed. The Tab order does not change: every item is still in Tab.
- `AppContext::focus_roving_edge(group, edge)` focuses the group's first or last item, choosing items by the same rules as the arrow keys (skipping disabled, unreachable, and inner-group nodes), scrolls it into view like `focus_node`, and returns the item that got focus. It applies pending reactive updates first, so an item whose visibility or enabled state was just written to a Store / signal in the same round already counts, and the caller does not need its own `flush_reactive`. It returns `None` when the group does not exist, has no items, or the item refuses focus. An event handler only has a `ViewContext` and cannot get an `AppContext`: call `dispatch_program` in the handler and call it in the program's `update`.

The column of capsules that rises above an entry point in the Dock combines the two: the entry has `has_popup`, `SecondaryPress` opens the capsule column, and `focus_roving_edge(column, press.focus.unwrap_or(RovingEdge::End))` focuses (the column is above the entry, so both ArrowUp and the menu key land on the last item, nearest the entry); the capsule column is a vertical group without wrapping, collapses on `RovingFocusEdge::End` (moving past the item nearest the entry), and returns focus to the entry.

Platform file drag and drop is lowered by the host into `InputPayload::FileDrag` (`FileDragKind::{Hover, Drop, Cancel}`). It is routed to the drop target by the input router. A node that is hit as a target emits `FileDropEvent::{Hovered, Dropped, Left}` and paints hover chrome. A node that has not registered receives no file drag and drop. Both hover and drop carry `modifiers`. The keyboard still belongs to the drag source while dragging. The host samples the system state on every mapping on Windows (`GetAsyncKeyState`) and macOS (`NSEvent.modifierFlags`). Linux falls back to the last tracked modifiers. The Windows OLE loop also re-sends a position when a key changes. So pressing Ctrl without moving the mouse still produces a new hover. The host accepts Copy. macOS also accepts Link (Copy takes precedence), because AppKit narrows a Finder drag with Control held down to Link. When only Copy is accepted the system refuses that drop. On a failed path read after the drop it emits `Cancel`. A drag never hangs. Losing or closing the window also ends the hover.

The line numbers, diagnostics gutter, minimap and git gutter of `TextArea` are view properties: `line_numbers` / `diagnostics` / `minimap` / `git_gutter`. Buffer revision, LSP and git state are still fed in by the application.

`TerminalView` is a retained grid. The application feeds `TerminalScreen` cells and styles. The framework emits `TerminalEvent::Input` / `Resize` / `SelectionChanged`. The PTY, submit and interrupt belong to the application (usually by interpreting Enter / Ctrl+C as writes to the PTY). When bound by tag (`bind_semantic`), the JSON of the `screen` property has the same shape as Runtime's `TerminalScreen`. `cells` can be a grapheme string (a wide character automatically takes two columns), or an array of strings / objects (when `width` is omitted, the display width of the first grapheme, 0/1/2). `foreground` / `background` are `[r,g,b]` or `[r,g,b,a]`: 0–1. Any RGB channel `> 1` means 0–255. Without `screen`, the picture fed in by the host's `sync_terminal_screen` is kept. High-frequency PTY frames still go through that Runtime API.

`DiffView` shows hunks fed in by the application. Accept / reject in `DiffEvent` is only a request. It does not change the buffer. `assemble_diff_view` assembles from the existing `ScrollView` + `Button` + `Text`. For read-only review (commits, workspace changes) use `.review_actions(false)`: accept / reject buttons are not assembled. Added and removed lines are backed with the success / danger colors at low opacity.

When you need to open a window, switch GPUs or write to disk, call `cx.dispatch_program(msg)` in the closure. It enters `RuntimeProgram::update` on the next frame. Do not do heavy work in a pointer handler.

## Form validation

Every control carries its own `invalid`. `FormField` carries `error`. `ValidationMessage` displays on its own. These three are the display layer. To ask "does this form still have anything filled in wrong" before submit, use `AppContext::validity_of(root)`. It reads the accessibility state the controls have already published. It returns every `invalid`, non-disabled field in the subtree, in document order.

```rust
let validity = cx.validity_of(form.stable_id());
if let Some(first) = validity.first_invalid() {
    cx.scroll_into_view(scroll, first, 8.0)?;   // Scroll to the first error
    cx.focus_node(document, first)?;
    return;
}
```

When the keyboard moves focus into a scroll container, `focus_node` (the path Tab takes) scrolls the focused node into every ancestor scroll viewport by the smallest distance. When the target is already fully visible the container does not move. The `scroll_into_view` call above comes first to leave a margin; the focus that follows sees the target already in the viewport and does not eat the margin again. A pointer press does not scroll: the target is already under the pointer, and scrolling it away would land the release somewhere else. `focus_node_in_place` does not scroll either, the equivalent of the web's `focus({ preventScroll: true })`, for applications that restore the scroll position first and the focus after. Axes that can move hand the current viewport offset and the reachable range to AccessKit; a generic container therefore projects as a scroll view, so the platform can see ScrollPattern. Percentages and viewport ratios are computed by the adapter.

Disabled fields do not count. A control the user cannot reach should not block submit. The validation rules themselves are still the application's. `validity_of` only reports what the tree currently says. It does not define what counts as valid.

## Text and lists

`TextInput` / `TextArea` hold the committed UTF-8, the selection and the IME preedit. They are the view-side editing model. Undo is supplied by Runtime (see below). The document revision, conflicts and persistence are still owned by the application. The optional `syntax-highlighting` feature enables a presenter named `"highlight"` on the same `TextArea`. It does not build a second editor.

`TextInput::character_counter(limit)` can optionally show the committed Unicode scalar count and the limit inside the field on the right;
over the limit it uses the danger color, the IME preedit does not count, and the editing area makes room for it automatically. The count is independent of the UTF-16 hard edit limit of `max_length`,
and it limits neither input nor submission; business gating is the consumer's. See [TextInput](https://github.com/sena-nana/NanaUI/blob/main/docs/components/text-input.md#字数计数).

Rust `TextArea::read_only(true)` keeps focus, cursor / selection, find and copy. It refuses modification, replacement, cut and paste. It differs from `disabled(true)`. A disabled control takes part in none of these. Switching to read-only at runtime ends an uncommitted IME composition and rejects a text drag-and-drop write already under way. The program can still provide new authoritative text through a component update. `HostedTextarea` forwards the same property. The semantic constructor property is `readOnly`. An application showing a read-only document should use this property, rather than substituting disabled styling for the read-only state.

### One editing entry point and undo

`RichTextEditor`'s `scroll_offset` is a viewport request; `UiWorld::scroll_offset` returns where it is actually painted.
The wheel can scroll while unfocused, keeping the selection, until the text or the cursor changes and cursor-follow resumes.
Painting, hit testing and the IME candidate box all read the same viewport.
It supports grapheme / word navigation and deletion, up and down and PageUp / PageDown navigation that keeps the column, Shift to extend, double-click to select a word, triple-click to select a paragraph, and drag-selection scrolling past the edge.
Rich text and ordinary input fields both keep keys for the IME first and then restore application shortcuts during composition.

An application edit menu can use `TextEditAction` and `AppContext::text_edit_action_enabled` to query state, and `edit_text_action(document, node, action, services)` to run undo, redo, cut, copy, paste and select all.
The clipboard is still supplied by the host's `HostServices`; copy and paste in the rich text editor keeps formatting and objects within the process, and a menu can call `AppContext::rich_clipboard(entity, RichClipboardCommand, services)` directly (`PastePlainText` included). Paste returns rich text only when the clipboard change sequence is still the one recorded at copy time; when the host supplies no sequence, text is matched instead. See [RichTextEditor](https://github.com/sena-nana/NanaUI/blob/main/docs/components/rich-text-editor.md#输入).
A source toolbar rewrite goes through `edit_text_area_value` and is recorded as one undoable step; rebinding the business document still uses an ordinary program write and clears the undo session.

The editor's text has **one write path**: `AppContext::commit_editor_edit(entity, origin, apply)`. Typing, deleting, pasting, IME commit, line transforms, snippets and application writes all funnel here. Everything that "must happen on every edit" happens in this one place: emitting the change event, recording undo. When you add a kind of edit operation, do not write `state.value` with your own `update_component`. Go through this entry point. Otherwise it does not enter undo.

`TextEditOrigin` says what the edit is. It decides whether it merges with the previous step:
- `Typing` / `Delete` — consecutive operations of the same kind merge into **one** undo step. Undo does not walk back one character at a time. Moving the cursor breaks the run.
- `Paste` / `Ime` / `Structural` — each is its own step. One IME commit is one step.
- `Program` — a value the application wrote itself (such as loading another document). It **clears** the log. Undo does not go back to the previous document's content.
- `History` — undo / redo itself. Never recorded.

The IME preedit lives in the world's `ime` slot, not in the editor's `value`. So the log never sees intermediate composition states. It only sees commits.

`undo_focused_text` / `redo_focused_text` act on the focused editor. They restore the selection from **when the edit started** (multiple cursors included). `can_undo_text` / `can_redo_text` gray out menu items. Input routing already wires Ctrl/Cmd+Z and Ctrl/Cmd+Shift+Z. Each editor is capped at 200 steps. They are released when the node is destroyed.

Clipboard: Ctrl/Cmd + C / X / V / A are wired by input routing to the focused editor. They sit after the application key policy and the terminal. Runtime only answers "what is selected" and "what this edit does" (`focused_selected_text`, `cut_focused_text`, `select_all_focused_text`, `replace_focused_text`). The system clipboard is held by the host. It is reached through `HostServices::read_clipboard` / `write_clipboard`. A native host shares one `OsClipboard` for the whole process. A headless session uses the private clipboard of `HeadlessHostServices`. When the backend is busy it answers `Busy`. It does not wait. Ctrl+C with nothing selected does not clear the clipboard. Ctrl+X on a failed clipboard write does not delete the text. A read-only field can be copied. It cannot be cut or pasted into. When focus is on `NativeMarkdown` / `SelectableRichText`, Ctrl+C takes its selection snapshot. An ordinary `Text` can be copied under `user-select: text | all | contain` (a document-level selection, not a second TextInput). `text` drag-selects. `all` selects the node's whole text on a single click. `contain` keeps the selection from extending to neighbours. An empty selection likewise does not clear the clipboard. Cut does not delete this read-only text. `user-select: auto` is not selectable by default. `none` does not enter the selection. An author's `::selection` / `::-moz-selection` `background` / `color` paint the selection highlight. When not written the selection backdrop uses the theme's `accent_soft`. On Android the slot's `HostServices` wires `AndroidClipboard`.

Large lists, tables and trees use `AppContext::materialize_virtual_*`. The window geometry is `VirtualListLayout::window`. No live nodes are built outside the visible window. Scrolling does not lay out the whole tree again. GPU nodes go through the same `ComponentRegistry` (`nana.gpu`, `nana.gpu-view`). Each control keeps only one tag. It equals the `ComponentTypeId` with the `nana.` prefix removed.

## Scrolling and scrollbars

`ScrollView` is the scrolling container. The authority for position is Runtime's `ScrollOffset`. The authority for size is `ScrollMetrics` (re-measured by Runtime when any commit that changes a layout box, child or style ends, with the offset clamped along with it; an axis that starts at the right / bottom edge has a negative offset, see [Layout](https://github.com/sena-nana/NanaUI/blob/main/docs/reference/layout.md)). The scrollbar does not keep its own offset. `overflow: auto|scroll` shares the same `ScrollOffset` and overflow clip (the wheel updates this offset too). But it does **not** paint a second thumb. Custom scrollbar chrome belongs only to `ScrollView`.

Touch (`PointerType::Touch`) starts scrolling the nearest scrollable container once the drag passes 8 logical pixels, and on release flings by the host's `ScrollPhysics` (iOS decay plus rubber-band bounce, or the Android spline fling clamped at the edge); the press is cancelled and fires no click. The contract is in [Runtime and Scene](https://github.com/sena-nana/NanaUI/blob/main/docs/reference/runtime-scene.md#触摸滚动与-scrollphysics).

`ScrollView::edge_fade(top, bottom)` fades the content out at the top and bottom edges of the scroll opening: the scroll area and its subtree compose into one destination group, alpha drops to 0 at the edge inside each band, so it works on a transparent background too, and the scrollbar stays outside the group and does not fade. Each band's length is `min(length, content beyond the edge)` and grows and shrinks with the offset. See [ScrollView](https://github.com/sena-nana/NanaUI/blob/main/docs/components/scroll-view.md#边缘渐隐).

`ScrollView::scrollbars` chooses one of three: `AutoHide` (fades in on hover or scroll, stays for the theme's `hide_delay` after leaving and then fades out), `Always` (resident while scrollable, with a track), `Hidden` (not drawn; the wheel and `scroll_to` still work). Unwritten, it follows the theme's policy `ScrollbarRecipe::visibility` (built-in `AutoHide`), and an application changes all of them at once with `ThemeDefinition::with_scrollbar_visibility`.

A scrollbar is an overlay. It takes no layout. The lane sits `track_inset` inside the padding box edge, and the container leaves at least `track_inset + thickness` of padding at the end, so the scrollbar does not touch the content. The scrollbar paints above every descendant of the scroll area, but still inside its clip and stacking context. While the pointer is over a visible lane (including a scroll area whose own container sets `pointer-events: none` while still showing scrollbars), hover and press belong to the scroll area: the lane activates, the thumb thickens, and the row below shows no hover. When both axes scroll they each give up the corner and never overlap.

The geometry is in the `scrollbar` module of `nana-ui-core` (`scrollbar_layout`). The sizes are in `ThemeMetrics::scrollbar`; the colors, strokes, motion and visibility policy are in the theme's `ScrollbarRecipe` (including `track`, `media_track` / `media_track_hot`, and `track_border` / `thumb_border` / `thumb_border_hot` slots). `::-webkit-scrollbar` / `::-webkit-scrollbar-thumb` or Rust callers override one node's thickness, surface context and colors through `ScrollbarSkin` (including `over_media`, `track_hot_color`, `thumb_hot_color` and border overrides), and still go through the same geometry and ordinary Scene quads, not a second thumb geometry engine. Thumb dragging and track clicks (pressing centers the thumb on the point) are handled by the `AppContext::begin_scrollbar_drag` family, through pointer capture.

## Adding your own control

Most needs are met by composing existing controls. To genuinely add a control that takes part in layout, clicks and painting:

1. Implement Runtime's `ComponentView` / `RegisterableComponent`. `ComponentView` requires `PartialEq`. Every field `project` reads must take part in the comparison. Equal writes are skipped. When `project` reads shared interior mutable state, or patches another component's node, declare `const ALWAYS_REPROJECT: bool = true;`.
2. Register it with `UiExtension` + `ExtensionRegistrar::register_component`. The stable identity is `ComponentTypeId` (such as `nana.button`, `app.preview-card`).
3. A registered tag equals the `ComponentTypeId` with the `nana.` prefix removed. Use the native tag when the semantics match HTML (`button`, `table`/`tr`/`td`, `ul`/`li`, `details`). Rename it when they differ (`search-dropdown`, not HTML's `<search>`). The tag and Rust's `create_component<C>` resolve through the same `ComponentRegistry`.

Live GPU content must not be made into "a control that paints itself onto the window". Use [Live GPU content](https://github.com/sena-nana/NanaUI/blob/main/docs/reference/gpu.md). Dynamically loaded dylib plugins are not supported.

`GpuTextureView` does not load web pages. `<iframe>` does not either. When you need in-app web content, use the host-native content exception `runtime::BrowserView`. It is not an alias of `GpuTextureView`. Only a macOS `WKWebView` implementation exists today. It is explicitly unavailable on Windows and Linux. The gallery must not present an ordinary texture or an iframe as a browser.

`GpuTextureView`, `Thumbnail` and `Avatar` sample only layer 0 of the host texture by default. The host should prepare sizes according to `HostTextureRegistry::painted_extent`. When the texture has a mip chain, use `.sampling(ImageSampling::Mipmap)` to switch to trilinear sampling. For the default resampling and mip options of `url()` images, see [Application API · Image sampling](https://github.com/sena-nana/NanaUI/blob/main/docs/reference/application-api.md#图片采样).

`Thumbnail` keeps control height × aspect by default. An explicit style's width and height, constraints and corner radius (a `style.radius` step or `border_radius` in pixels) take precedence. It can serve as a responsive card cover. When none is written it takes `Xs`. `fit(ContentFit::Cover)` keeps the cover crop. The default is still Contain. Empty, loading, ready and unavailable share the layout size. The loading spinner is painted centered. Its edge is 28 (twice a compact `Spinner`). A standalone `Spinner` with a label still sits left as the slot before the text. A cover badge hangs as a child of the Thumbnail. The control is a containing block (`position: relative`) and clips to the corner radius. `Thumbnail::badge()` gives a solid badge in the bottom-right corner that does not hit. `Thumbnail::pickable()` (template `pickable=true`) has the control take the pointer itself and report hover, leave and primary press as `ThumbnailPick` with image coordinates (`0..=1`); `intrinsic_size` gives the texture size in pixels, and the Contain letterbox and the part cropped by Cover are not reported. The control does not take focus; the host provides a keyboard alternative in the list. See [Thumbnail](https://github.com/sena-nana/NanaUI/blob/main/docs/components/thumbnail.md#在图片上拾取).

### Charts and icon buttons

Rust inline heading tools use `IconButton::compact(true)`: a fixed 24×24 logical px,
keeping standard icon, focus, tooltip, selected and disabled semantics, and not growing with ordinary control density.
`Popover::compact_trigger(true)` and `ActionMenu::compact_trigger(true)` give the icon trigger
the same size recipe; a custom content trigger instead becomes exactly the content size (no padding, no fixed height,
which is what the `ColorField` swatch does); text triggers are unaffected. The anchor keeps its size while the menu is open.
These options are off by default; off, they restore the original `size` / theme size. A menu entry with no resting background
can also be given `bare_trigger(true)`, and the menu surface and items still use standard sizes.

`Chart::new(option)` paints a chart. `ChartOption` mirrors ECharts' `option` (`grid`, `x_axis`, `y_axis`, `series`, `tooltip`, `legend`, `data_zoom`), with Rust types as values, and the model lives in `nana_ui::runtime::chart` (the `nana-ui-charts` crate). Series include line / area, bar, pie / donut / rose, scatter, radar and gauge. Swapping the option is one update: elements transition from where they are on screen to their new positions. Hover triggers per category or per item, emphasis and the axis pointer are painted by the shader on the motion clock, and the tooltip is the chart's own overlay, with color dots and right-aligned values. It closes on leave, unmount or park. Legend toggles and the zoom window live in `Chart::view`, and events are `ChartEvent`. Data, names and number formats are still supplied by the application. See [Chart](https://github.com/sena-nana/NanaUI/blob/main/docs/components/chart.md).

`Chart` is only created from Rust: the option is typed data and has no tag.

`Button::icon(icon).icon_size(px).icon_gap(px)` measures, centers and clips the icon and the text as one content group. It keeps a button's Activate, focus and disabled semantics. Loading replaces the icon with a spinner instead of stacking a second slot. A change only in the spinner phase does not trigger layout. `trailing_icon(icon)` puts a second icon after the text (the chevron of a selector or menu button). Size and spacing follow the leading icon. When the width runs out the text is clipped first. Both icons keep their size.

### HoverCard editor focus

`HoverCard::preserve_editor_focus(true)` is for non-modal helper cards such as a QR scan. Off by default. When the pointer hits the trigger or an action in the card, the editor focus and selection outside the card are kept. Buttons still activate normally. Tab / Shift+Tab still reach the accessible actions. Focus that entered from outside the card through the keyboard returns to the most recent valid outside focus when the card closes. It is also restored when the card or the current action is hidden, parked, disabled or deleted. An explicit focus request and scope restoration take precedence. A stale or invisible restore target does not get focus again. The content container must take part in hit testing (for example `Stack::column(...).hittable()`), so mouse events on the QR code and the blank area belong to the card. `QrCode` itself is still a non-focusable accessible Image.

### Adaptive multi-line composer

`TextArea::auto_grow(1, 6)` (a Rust constructor property) grows and shrinks by the visual text lines after actual layout, and scrolls inside the editing area past the maximum line count. It is off by default; an ordinary `TextArea`'s size and Enter-to-newline behavior do not change. `character_counter(limit)`, like `TextInput`, counts only the Unicode scalars of committed text, shows the error color over the limit, and does not truncate input.

With a minimum of 1 row and a counter or action slot enabled, short text stays a compact single line (32px by default), with the counter and the actions at the right inside the field. Only when the text would cross the counter's left boundary or the usable boundary left of the actions, or when there is an explicit newline, does it expand into a full-width editing area above and an action bar below. The decision is measured by the same host text engine on the displayed text (IME preedit included) and always compared against the assumed compact row width; once expanded it does not flip back and forth even when the full width would hold one line. Deleting, cancelling the IME and width changes can return it to the compact single line; placeholder text does not trigger expansion.

`submit_on_enter(true)` makes Enter emit `TextSubmitted`, while Shift+Enter still inserts a newline; Enter is not sent while the IME is composing. Read-only and disabled do not submit. The application validates and handles the submission.

`.trailing_action(view)` on `view::text_area()` or `view::widget(TextArea::new(...))` puts real action controls in the small control slot at the right inside the field. When expanded, the action bar's height is reserved through the bottom padding, and the text, soft wraps, cursor, selection and IME all use the full width above. The actions have their own focus, Activate and accessible names, and the key path stays under the field. Imperatively, use `TextArea::trailing_action(node)` and then call `AppContext::assemble_text_area`.

`auto_grow`'s line count does not include the bottom action bar. When expanded, the counter plus one line of actions is 64px (a 32px single-line input + 28px small actions + 4px gap), and the six-line text cap is 144px; with only a counter the bottom bar is 16px plus a 4px gap. `min_rows > 1` keeps the multi-line bottom bar layout. In both the compact and expanded states, a height-constrained Flex parent may shrink to the corresponding minimum, with the rest of the content scrolling inside; an explicit `flex_shrink` policy from the consumer is kept.

`PathText::new(full_display_path)` is a read-only path summary; pass `display_path(path, false)`, and the business keeps the real path separately. `LabeledValue::path_value` and `SettingsRow::path_hint` provide the same behavior. A Rust view can bind `value_is_path` / `hint_is_path`; the full-path tooltip is queried with `AppContext::component_tooltip` and follows the shared overlay lifecycle.
