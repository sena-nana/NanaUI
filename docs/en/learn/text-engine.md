# Text engine: `nana-text`

This chapter goes deep into `nana-text`: the framework's only authority for text measurement, OpenType shaping and retained text layout. By the end you can answer: within one `TextEngine::layout` call, what each of the three stages does ("font selection → text shaping → line layout") and where the cache boundaries sit; how the font layer uses generations (`FontGeneration`) and `cmap` coverage to decide "which font face each grapheme cluster uses"; why decoupling line layout from shaping completely makes continuous window resizing cost only line breaking rather than a shaping rerun; and how the Runtime keeps text layouts across frames through `TextLayoutStore` generation handles.

## Responsibilities and boundaries

`crates/nana-text/src/lib.rs` (`:7-21`) defines the territory of the text stack precisely:

- **Stage one: the font layer (#90)**: font registration, generation management, font face matching, variable-font axis coordinate resolution and missing-glyph fallback based on `cmap` coverage.
- **Stage two: OpenType shaping (#91)**: grapheme cluster / script / bidirectional text (BiDi) segmentation, HarfRust shaping and a bounded shaping cache (`ShapeCache`).
- **Stage three: paragraph line layout (#92)**: the single-line label fast path, greedy wrapping over UAX #14 break opportunities, per-line BiDi visual reordering, line box metrics, alignment, ellipsis truncation and a bounded layout cache (`LayoutCache`). `NativeTextEngine` gathers these three stages behind the single entry point `TextEngine::layout`.
- **Stages four to eight: retained handles and the single product authority (#95 / #99)**: text nodes in `UiWorld` keep their layout results through `TextLayoutStore` generation handles, Rust L3 and `.vue` both measure through the same process-level engine, and `SceneWgpuPainter::text` in `nana-ui` draws the retained `TextLayout` directly.
- **Low-level algorithm encapsulation and vocabulary borrowing**: `cosmic-text` and `cryoglyph` have been removed from the dependency graph entirely (guarded by `scripts/check-engine-boundary.py`); low-level standard libraries (`fontdb`, `memmap2`, `skrifa`, `harfrust`, `unicode-bidi`, `unicode-linebreak`, and `zeno`/`png` behind the optional `raster` feature) stay strictly sealed in their own private submodules and never leak into public signatures (`icu_properties` and `swash` are disallowed as well); typography vocabulary and shared helpers (the 12 items listed in `lib.rs:34-37` and the 19-item `NANA_TEXT_CORE_ALLOWLIST` in `scripts/check-engine-boundary.py`, such as `FontVariationSetting`, `LineBreakSpec`, `WritingModeSpec`, `dynamic_layout`, and `sort`) are imported directly from `nana-ui-core` rather than redefined.
- **Cursor and editing are pure derivations over the IR**: cursor placement, hit testing and selection rectangles are pure functions over a completed `TextLayout` (`crates/nana-text/src/edit.rs`) and do not pollute engine cache state.

## Internal structure

### 1. One call threading three stages: `NativeTextEngine::layout`

`TextEngine::layout(kind, source, base, constraints, counters) -> Arc<TextLayout>` (`crates/nana-text/src/engine.rs:38-45`) returns an immutable shared `Arc` — the same text with the same constraints hits the cache on later frames and receives the same pointer. Its internal implementation (`engine.rs:371-468`) advances through a fixed six steps:

1. **`fold_lines` (`:194`)**: under `white-space: normal`, newlines in the source are folded into spaces — the shaper and the line breaker must see exactly the same byte stream, so folding happens **before** shaping;
2. **`shape` (`:180`)**: builds a `ShapeRequest` from `base.language` or the engine default language and hands it to the `Shaper`, producing an `Arc<ShapedText>`;
3. **ellipsis shaping (`shape_ellipsis` `:272`)**: runs `const ELLIPSIS: &str = "…"` (`:25`) through the standard shaping path so that every truncated node in the same style shares one ellipsis cache entry;
4. **`strut_metrics` (`:292`)**: computes the strut metrics of the base style's own font face, used to lock the minimum line box height and baseline so a taller fallback glyph on the same line cannot tilt the baseline (cached by `(FontInstanceKey, canonical_f32_bits(size))` in a `BoundedCache` with capacity `STRUT_CAP = 1024`, `:78`);
5. **ruby, emphasis, and inline object label shaping (`:389-430`)**: each shaped at its proportional font size;
6. **line layout and counter diffing (`:431-467`)**: assembles the `LayoutRequest` and hands it to `Layouter::layout`, then writes this pass's cache hit/miss, resolved glyph and break opportunity deltas into `TextWorkCounters`.

### 2. The font layer: registration, generations and `cmap` coverage fallback

`FontSystem` (`crates/nana-text/src/font/system.rs:1-31`) maintains three core guarantees:

- **Byte lifetime decoupled from handle retirement**: font bytes are wrapped in `FontBlob` (`Arc`); unregistering a face only retires its `FontId` handle and never takes away bytes that background readers are still using (`:4-12`).
- **Bidirectionally precise generation invalidation (`FontGeneration`)**: every registration, unregistration, system font load or fallback policy switch increments `FontGeneration` (`:18-31`). The selection cache is cleared wholesale (a newly registered font may change the winner for any family list), while the `cmap` coverage cache removes only the exact faces that were unloaded; slots of retired `FontId`s are never reused by generation.
- **Deterministic selection and explainable diagnostics**: `FontQuery` (family list, weight, width, slant, language) combined with `FontOrigin` priority (explicit registration beats the system font scan, `:63-80`) and `FaceDescriptor` (`@font-face` declared family names override the names inside the font's own tables, `:88-97`) selects a face and records `FontChoiceReason` and `FontAssignment`, so diagnostic tools can answer precisely "why did this piece of text land on this fallback font".

### 3. The shaping layer: segmentation, BiDi, HarfRust and a bounded fallback budget

`Shaper` (`crates/nana-text/src/shaping/shaper.rs:27-34`) first splits the text source into **style segments (`StyleSegment:43`)**, then splits those into **items (`Item:51`)** by same style, same BiDi embedding level, same Unicode Script and same upright/sideways orientation, and splits items into **pieces (`Piece:64`)** by font face `cmap` coverage (the `U+FFFC` inline object placeholder never enters the shaper, `:268`).

To keep a stretch of rare or corrupt characters from exhausting every system font, fallback has two hard budgets: `MAX_FALLBACK_CANDIDATES_PER_RANGE = 8` (at most 8 candidate faces tried per missing-glyph range) and `MAX_FALLBACK_RETRIES_PER_ITEM = 32` (at most 32 retries per item, `shaper.rs:21-24`). Vertical text is split at shaping time under UAX #50 into upright runs (using the font's vertical metrics `vert` / `vrt2`) and sideways runs (shaped horizontally, rotated 90° clockwise when drawn).

### 4. The line layout layer: decoupled from shaping, UAX #14 wrapping and the `TextLayout` IR

The core design of `layout/mod.rs` (`crates/nana-text/src/layout/mod.rs:4-17`) is **fully decoupling line layout from OpenType shaping**: the `Layouter` only reads an already-shaped `ShapedText` and slices it into lines, never calling HarfRust again. So **when window drag-resizing changes the container width, the wrap mode is switched, `max_lines` is modified or horizontal alignment changes, only the lightweight line layout module reruns and the existing shaping cache is fully reused**.

Each line's termination reason is recorded precisely by `LineBreakCause` (`ir.rs:127-138`):

| Variant | Meaning |
| --- | --- |
| `Explicit` | An explicit newline `\n` in the source text |
| `Wrap` | Automatic wrapping triggered by exhausting the line width budget |
| `MaxLines` | Truncated by reaching the `max_lines` limit |
| `MaxHeight` | Truncated because the next line does not fit the `max_height_px` height budget |
| `EndOfText` | The natural end of the text |

Under vertical writing (`vertical-rl` / `vertical-lr`) line layout reuses the same code as horizontal in "line-relative coordinates"; only three places in the whole engine know the page turned: the line budget reads the container height instead of its width (`TextConstraints::inline_budget_px`), line boxes use the central baseline instead of the alphabetic baseline, and the final physical coordinate mapping (`physical_x_of_block` / `physical_size`, `ir.rs:268, :297`). Staleness costs one $O(1)$ two-integer comparison: `layout.is_stale(revision, font_generation)` (`:338-340`).

### 5. `TextLayoutStore`: retained handles versus the cache boundary

An ordinary LRU/FIFO cache evicts entries whenever it likes, but a layout attached to a retained tree node needs a handle that "lives and dies with the node and explicitly rejects access across worlds or from an older generation" — that is the job of `TextLayoutStore` (`crates/nana-text/src/layout/store.rs:54`). Slot generations come from the process-wide monotonic sequence `NEXT_GENERATION` (`:23-32`), and `resolve` checks both the slot generation and `FontGeneration` (returning `StaleLayout::Retired` or `StaleLayout::FontGeneration` when stale).

## Collaboration and data flow

`UiWorld` holds the process-level shared engine through `paint_text_engine: Option<nana_text::SharedTextEngine>` (`crates/nana-ui-runtime/src/world.rs:1135`) and keeps `text_nodes: DenseNodeMap<TextNodeState>` in a separate table inside `NodeStore` (`crates/nana-ui-runtime/src/store.rs:1048`), so large layouts can skip nodes with no text change. In `resolve_plain_text` (`world/text.rs:4045`), if the truncated layout carries `OverflowFlags::ELLIPSIZED` and the parent box needs a natural width, the Runtime queries a natural layout once more with unbounded constraints to obtain the true maximum width before wrapping. The `TextLayoutId` finally retained on the node travels with `ExtractedNode` to `UiScene`, and `SceneWgpuPainter::text` reads the glyph runs directly, rasterizes and presents them.
